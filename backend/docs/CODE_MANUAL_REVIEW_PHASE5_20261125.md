## 2. 已有能力的实际分工

- `cad_plan_references` 处理构造计划内的 output/object/assembly 名称，拒绝歧义和错误引用。
- `cad_candidate_state` 把符号映射绑定到项目、版本和实际几何哈希，并记录有执行来源证据的复制事件。
- `logical_topology` 管理对象归属、整体身份、共享图元、对象关系及编辑前后连续性。
- `cad_revision` 用几何快照、验证和逻辑连续性建立版本证据；规划再复核这些绑定。
- `spatial_partition` 切分已有路径，保留来源 ID、共享归属、跨区连接、局部坐标和执行段。

这些模块不是功能完全相同的重复品，不能因都涉及 ID、哈希或关系就合并删除。需要整合的是各阶段之间的实际几何、身份映射和证据协议。

## 3. 新增复现：三类根因，四个具体场景

证据为 `phase5_probes.py` 与 `phase5-probes.json`。使用现有隔离环境，调用实际编辑执行器、v2 合同、对象图演化、版本校验、目标解析和分区函数。没有伪造验收通过，没有运行 HTTP 最终响应、候选保存或设备执行。

### 3.1 新增副本没有刷新边界，版本通过后仍影响下一轮选择

来源为中心 `(0,0)`、半径 500 毫米的圆，对象边界 x=-500…500。通过图元选区向右复制 3000 毫米：

- 实际副本中心 x=3000，几何边界 x=2500…3500。
- 副本获得新几何 ID、对象 ID、整体 ID 和 `derived_from_object_id`，这些身份能力确实存在。
- 副本对象的 `bounds` 却仍为 x=-500…500，与原圆重合。
- 对象图校验通过，`build_cad_revision_contract.status=verified`。
- 随后请求最右侧圆，真实 `resolve_logical_object_target` 返回 `needs_clarification`，原因 `equal_logical_position`。

根因：选区复制分支直接复制原对象，包括旧边界；最后调用的 `_refresh_changed_object_bounds` 只检查“来源与目标共有 ID 且内容改变”的几何。纯新增副本没有此类 ID，因此提前返回。不是没有空间选择器，而是交给选择器的对象状态已过时。

证明范围到实际版本校验和下一轮目标解析；不等同于完整 HTTP 正式交付复现。

### 3.2 仅删除部分图元，也会保留旧对象范围

一个组合对象引用两个 1000×1000 毫米矩形，分别位于 x=0…1000 和 x=3000…4000，对象范围 x=0…4000。明确删除第二个图元：

- 执行器正确留下第一个矩形，输入没有被修改。
- 演化后的对象引用正确变为 `[1]`，但 `bounds.max_x` 仍为 4000，实际应为 1000。
- 对象图和版本验证仍通过。

这是同一边界刷新根因的删除场景：对象成员减少，但保留 ID 下的几何没有改变。当前刷新发生在删除分支更新 refs 之前，并且不处理仅删除成员的情况。

不能简单把所有对象边界改成图元包络：已有测试明确保留“房间区域仅由共享分隔线表示”的二维区域范围。后续需区分实际路径边界与语义区域边界，对无歧义完整几何刷新，对区域范围保留来源或标为待确认。复制时也可依据有证据的实际变换更新语义区域，而不能盲用单根分隔线范围。

### 3.3 复制共享边：已有实现被连续性合同阻断

两个逻辑对象共同引用中间边，来源共享声明合法。选择包含它们的整个实例或全部三个图元，向右复制 4000 毫米：

| 目标表示 | 执行几何 | 演化后对象图 | 版本结果 |
|---|---|---|---|
| 实例 | 成功 | 副本对象共用新边，却没有对应共享声明 | 拒绝，`missing_shared_declaration` |
| 全部图元选区 | 成功 | 已复制共享声明，图校验通过 | 拒绝，`shared_topology_drift` |

这里存在两个衔接缺口：

1. 旧实例复制分支只克隆对象，没有克隆共享声明和内部关系。选区复制分支已经有这项能力，不应再新建第三套。
2. `validate_logical_object_continuity` 将新增共享声明也算入 `shared_geometry_changes`，而只给 `translate + split_shared` 开放改变许可。合法复制产生的新共享边因此被一并拒绝，即使原共享归属没有改变。

后续应分别证明“原共享归属保持”“新共享归属由复制映射派生”，不能直接关闭共享拓扑保护。当前证明版本层正确拒绝了不符合现行合同的结果，没有证明错误结果已保存。

### 3.4 单个长路径突破执行段的 500 米预算

使用一个 10×18 米范围内的开放蛇形多段线，61 条横向段及连接段，实际总长 628 米；单区足以覆盖其空间范围：

- `build_spatial_partition.status=ready`。
- 来源与分区路径均为 628 米，覆盖和坐标往返验证通过。
- 最终只有一个执行段，`printing_length_m=628`，超过现有常量 `MAX_SEGMENT_PRINTING_LENGTH_M=500`。

原因：`_execution_segments` 只在已有当前组时按长度换组；单个 fragment 自身超长时不拆分，也不拒绝。空间尺寸小不代表路径总长短，增加网格并不总能解决此问题。

这是已有分区函数的预算边界问题。本轮没有执行任务，不据此推断真实设备已经收到或完成超长任务。该问题应记录，但不挤占自然语言来源与对象状态衔接的优先级。

## 4. 对象图校验并非完整几何关系实测

`validate_logical_object_graph` 核对 ID、refs、共享归属、整体名称及关系端点。其空间关系检查主要读取对象已有 `bounds`，不从传入几何重测所有对象。

这解释了旧边界为何可以连同版本验证一起通过：合法引用和哈希绑定证明保存的内容一致，没有证明每条元数据都对应当前真实曲线。后续报告必须区分图引用完整性、空间元数据时效性和独立几何关系验收。

现有测试覆盖了平移和改半径后的刷新，但复制测试主要检查新 ID、refs、整体归属和图校验，没有验证副本边界；共享复制也不能由单对象复制测试推导为完整支持。

## 5. 查重：应清理的旧辅助函数与不能夸大的缺陷

`cad_project_candidates.scale_factor_from_message` 和 `scale_geometries` 与当前增量编辑中的缩放解析和变换具有重复职责。本轮搜索 `app`，未发现这两个整体缩放函数的生产调用点；不能把定义存在当作正在运行的第二条缩放生产链。

两套解析语义也不同：

| 原文 | 增量解析 | 旧整体缩放辅助函数 |
|---|---:|---:|
| 缩小到0.5倍 | 0.5 | 2.0 |
| 缩小到原来的0.5倍 | 0.5 | 无结果 |

这是清理和防误用的证据，不是本轮证明的生产缩放回归。删除前仍需搜索测试、脚本及外部导入，保留需要的兼容接口。

### 5.2 单位兼容分支提前返回，但当前生产调用不触发

`normalize_model_geometry_units` 对水平线显式传入 `m` 时，因高度为 0，先返回 `degenerate_extent`，没有把终点 x=1 换算为 1000 毫米。显式单位换算不应依赖二维面积非退化，这一点已函数级复现。

但当前 `app` 中唯一调用位于 `cad_construction_commit`，固定传入 `explicit_units=mm`，因为执行器已经换算过。该调用提前返回 `declared_mm`，不受此缺陷影响。**不把这一兼容分支问题算入当前模型生成链路的已证实失败。**

### 5.3 兼容生成与正式构造要按调用条件评定

`design_geometries_for_project` 仍保留矩形、心形、圆和拱门的旧兼容构造，前面先尝试现有模板计划解释；正式结构化构造另有统一 IR。它们的存在应纳入重复能力地图，但不能仅凭形状分支相似，就假定所有入口都在重复调用或直接删除历史兼容。
