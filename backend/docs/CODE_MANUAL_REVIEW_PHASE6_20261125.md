## 3. 四处新增衔接问题

### 3.1 工具流异常结束仍被送入分发，结构化构造流则拒绝

位置：`_chat_stream_impl` 第 2444 行起，对照 `_deepseek_request` 第 2094 行起。

向两个现有读取路径注入相同的未完成流：先收到一条 JSON 参数完整的工具增量，随后直接 EOF；另一个样例在 EOF 前额外收到 `error` 事件。

| 输入情况 | 普通工具流 | 结构化构造流 |
|---|---|---|
| 没有 `finish_reason`，直接 EOF | 仍到达工具分发边界 1 次 | 抛出提前中断错误 |
| 已收到供应商 `error`，随后 EOF | 仍到达工具分发边界 1 次 | 抛出流式构造失败错误 |

原因：普通流循环未验证完成原因，也未处理 `event.error`；读取结束后直接使用已积累的工具调用。结构化流已有完成原因和错误事件检查。这是现有协议实现不一致，应复用已有生命周期判定，不能再增加一套“可靠流读取器”而保留旧分支继续工作。

样例的成功返回来自记录器，专门用于证明分发边界被到达，不能写成“生产已错误执行”。具体工具仍有参数、策略、确认和保存门槛。

同一复现还确认请求构造差异：结构化请求为 `deepseek-flash` 添加 `thinking.type=disabled`，普通工具流直接构造 payload，没有此字段。这证明代码策略不一致，没有证明在线模型响应差异或波动比例。

### 3.2 流式超时包装丢掉已实现的响应套接字回退

位置：`_set_deepseek_socket_timeout` 第 2822 行起，对照 `DeepSeekTransport.set_socket_timeout`。

传输层已实现：当 `connection.sock` 为空时，可以从 `response.fp.raw._sock` 找到套接字。结构化流传入 `response`，普通流调用服务包装时只传连接和 deadline。

使用相同的模拟连接（`sock=None`）和响应：

- 服务包装调用的 `settimeout` 次数为 0。
- 直接调用现有传输层并传入响应，次数为 1。

传输层在建立响应时已有初始超时设置。这里确认的缺口是后续逐次读取刷新剩余 deadline 时，包装未携带响应，无法使用已有回退；没有实测真实网络阻塞时长，也不声称所有流请求都没有超时。

### 3.3 独立图纸预演丢失原逻辑对象和拓扑

第二轮已确认 `modify_drawing` 当前还存在登记/分发不一致，本样例直接调用已有预演方法，不能据此宣称正常入口已经写坏文件。修复分发前应一并处理载荷语义保留；只接通分发并不能证明独立编辑已经完整。

### 3.4 全局 CAD 规划模型配置无法往返保留 flash

位置：`cad_planning_model` 属性、`update_config` 和 `_load_config` 第 528 行起。

在 `local-default` 全局配置路径、未设置 `DEEPSEEK_CAD_PLANNING_MODEL` 的条件下，使用真实配置方法和临时文件：

1. 保存 `cad_planning_model=deepseek-flash`，返回值为 flash。
2. 文件中也保存 flash。
3. 将内存字段重置到默认值，调用真实 `_load_config`，得到 `deepseek-chat`。

原因：属性允许 chat/reasoner/flash，保存方法也写入 flash；载入白名单仍只有 chat/reasoner。现有全局往返测试只覆盖 reasoner。

本项限定为全局配置载入。环境变量直接指定 flash 时不走这个覆盖条件；用户独立配置存储是另一条路径，本轮没有把该结果扩大成所有用户都会切换模型。它也不能直接解释既有某次评测为何由通过变失败，仍需要当轮请求记录支持。

## 4. 查重与现有能力边界

### 4.1 请求生命周期重复，供应商格式差异需要保留

主服务仍直接管理部分供应商网络请求、用户请求租约、SSE 累积、完成判定和 payload 参数。已有 `model_request_gateway`、`DeepSeekTransport`、`structured_usage` 分别管理调用准入、传输和请求内用量记录。

可以统一的是准入、连接关闭、完成/错误状态和请求参数策略。Anthropic/Gemini/OpenAI 的消息、工具结果和响应格式需要各自适配，不能用删掉所有格式分支的方式“统一”。结构化 JSON 重试、几何有限修复和项目级重试也不是同一种重试，预算应跨层可追踪。

`structured_usage` 是请求内结构化调用汇总；手工评测预算账本位于测试/评测工具。不能将请求网关的存在等同于已经具备完整的供应商费用结算证明。

### 4.2 独立文件与项目候选有两个持久化域

独立文件编辑已有文件哈希、版本、操作幂等、选区绑定、差异、路径影响和预览；项目候选已有 v2 命令、对象图演化、机器断言、版本与验收。二者可以共享几何和证据组件，但文件版本与项目候选版本不能直接互换。

### 4.3 未找到调用点的旧函数单列，不当作生产能力

在 `app/tests/scripts/tools` 搜索 `_recover_incremental_copy`，只有定义和其内部辅助函数调用，没有找到外部调用点。该旧方法仅平移父几何，没有创建并保留源加副本的新 ID 集，也没有构建复制命令，因此不能据名称算作另一套完整复制能力。其单位正则也与当前编辑解析器重复。

`_discarded_mojibake_drive_intent` 同样仅找到定义。它是清理候选，不应与实际仍调用的基础运动解析一起计为多条生产能力。

### 4.4 正式生成入口已有适配整合

`_deterministic_design_confirmation` 已明确适配到 `_formal_cad_construction`；模板本地模式也接入该入口。`generate_project_candidate` 对确认项目有独立的一次重试策略，不能将其与内部局部修复预算混算。某些旧方法已是适配器，不能看到旧函数名就误判为仍有第二套生成器。
