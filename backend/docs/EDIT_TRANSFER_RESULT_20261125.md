# 组合生成到编辑/歧义处理的冻结测试

本批新增一个三对象组合与两类编辑，各重复两次：基图生成**4/4**，明确编辑正式交付**0/4**，歧义请求合格澄清**0/4**。不能用此前生成留出12/12推断编辑可靠。

四条均有本轮正式合格基图，因此没有基图前置阻塞。但后续请求在编辑或歧义处理前走入错误的项目/候选交付链路，不能将0/4解释为几何编辑工具本身无法实现这些操作。

## 需求及口径

基图为左圆(-1600,800)、半径340毫米；右圆(2100,800)、半径220毫米；下矩形左下(-400,-1300)、宽900、高650毫米。三对象同图、独立、不加连接或标注。

每条工作流先发送“把圆的半径改为460毫米”，没有指定两个圆中的哪一个，预期澄清且不提交候选；随后E1明确将左圆半径改510毫米，或E2明确将下矩形向右移动230毫米。两个请求均携带原项目和原版本ID，空history，不注入对象ID/选择。各仅一次聊天调用；不补参或额外确认。

明确编辑期望全图独立边界比对通过、其他对象保留、原版本不变、新正式候选已保存且响应预览一致。歧义澄清需要明确澄清信号并且不提交候选，不能仅凭原图不变给分。

这是开发者内部小范围工作流测试，只有一个组合和两类编辑，不能代表全部编辑或任意CAD需求。尚未隔离歧义请求对后续明确编辑的上下文影响；当前失败发生在更早的项目/候选绑定阶段，后续修复应补充独立分支对照。

## 全部失败现场与根因边界

E1-r1、E2-r1、E1-r2出现以下相同现象，E2-r2的歧义请求另有下述生成失败：

1. 新基图在原项目正式保存，独立几何通过。
2. 歧义请求未返回合格澄清，反而在另一个新项目提交候选。
3. 明确编辑也在第三个项目提交候选，没有在原项目交付新编辑版本。
4. HTTP保护返回`candidate_not_bound_to_current_run`并隐藏候选，用户消息为“候选尚未通过当前运行的几何验收或版本绑定检查”。

前三条工作流最终各三个项目、各一个候选；E2-r2有两个项目、各一个候选。E2-r2歧义请求没有新增候选，但返回生成失败：实际中心距2423.45，模型要求2563.2，并未澄清哪个圆；其后明确编辑也提交到错误的新项目。全部原项目版本未改。**这并非无副作用的安全澄清**：测试原先局部记录的`unchanged=True`只指原项目，新增项目/候选已在跨项目诊断补充完整记录，未因此加分。歧义和明确请求各四条，共八条请求未交付预期结果，其中七条发生错误新项目候选提交。

例如E1-r1原项目328bfdcd…，歧义请求提交到b8d1bbc0…，明确编辑提交到883ed851…；后两项均被运行绑定保护隐藏。完整ID、请求body、候选和运行ID保留在`cross-project-diagnostic.json`和原始step/projects中。

证据支持“编辑请求在交付前错误进入新项目生成/提交路径”，尚未完成逐函数归因，不能声称已经排除所有请求上下文/测试配置因素。检查到的保护动作是正确的；下一步应追踪HTTP请求携带的project/variant如何转成意图、来源快照和候选提交目标，不能通过删除绑定保护让旧候选或错误新项目通过。
