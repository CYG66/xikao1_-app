## 二、共享文件的三条判据

一个文件是不是"共享"，不看它被 import 多少次，看这三条：

1. 它是否定义跨线数据结构（Pydantic 模型 / 字典契约）→ 是，则冻结，改需提案。
2. 它是否被两条线在阶段二同时修改 → 是，则指定唯一负责人，另一条线提需求。
3. 它是否是验收闸门（H2/H3/H4 判定）→ 是，则只有该闸门负责人可改，且不得放宽。

`backend/app/agent_service.py` 同时满足 1 和 3，因此只归 C，且 C 不得借"链路修复"之名改验收语义。

## 三、五类公共接口（冻结）

以下字段名不是建议，是**现有代码事实**；改动它等于改动所有人的输入输出。

### 1. CAD Plan（构造计划）

- 根模型：`CadConstructionPlan`，`schema_version = "cad.construction-plan.v1"`
- 关键顶层字段：`units`（`m` / `mm`，默认 `m`）、`project_id`、`source_version`、`steps`、`constraints`、`constraint_backend`、`assertions`、`budgets`、`free_outline_layout`
- 复合路径：`AddCompositePathStep`，含 `segments`、`closed`、`samples_per_curve`（默认 32，8–128）、`connection_tolerance`（默认 1e-6）、`continuity`（`C0` / `C1`）、`tangent_tolerance_deg`（默认 1.0）、`allow_self_intersection`（默认 `False`）、`allow_duplicate_segments`、`max_curvature`、`max_sampling_error`、`junction_constraints`

冻结理由：这是 A 的输出与 B 的输入，字段一改两边同时返工。

### 2. Junction Constraint（交点约束）

`JunctionConstraint` 现有字段（**不得增删改名，除非提案获批**）：

| 字段 | 类型 / 约束 | 语义 |
|---|---|---|
| `junction_index` | int ≥ 0 | 第几个连接点 |
| `left_segment_index` | int ≥ 0 | 左侧段索引（0 基） |
| `right_segment_index` | int ≥ 0 | 右侧段索引（0 基） |
| `intent` | `smooth` / `intentional_cusp` / `intentional_corner` / `unknown` | 设计意图 |
| `required_continuity` | `C0` / `G1` / `C1` | 要求的连续性 |
| `tangent_tolerance_deg` | float>0 且 ≤45，可空 | 切线夹角容差 |
| `source_requirement_refs` | list[str]，≤20 | 该约束来自哪条需求 |

**已内建校验**（改动前必须先读 `cad_construction.py` 的 `validate_intent_continuity` 与 `validate_junction_constraints`）：

- `smooth` 不得配 `C0`（必须是 `G1` 或 `C1`）
- `intentional_cusp` / `intentional_corner` 必须是 `C0`
- 连接点索引必须落在 `segments` 范围内且不重复

A9 的 `junction_constraints` 为空，意味着上述意图声明整段缺失——不是"少了一个字段"，而是"模型从未表达过连接意图"。

### 3. Requirement（需求契约与来源）

- 契约构造与来源索引在 `cad_requirement_contract.py`；来源索引结构形如 `{"request_id":…, "project_id":…, "entries": {…}}`
- `validate_junction_source_refs(junction_constraints, source_index)` 的语义是**只校验、不创建**：`source_requirement_refs` 只能指向已存在且 `source_status == "valid"` 的条目；未知引用直接判失败，不得自动升级来源。
- 冻结要求：任何一条 junction constraint 必须能追到一条有效需求；追不到就是不合格，不允许"补一个来源"绕过。

### 4. Geometry（几何输出）

- 单位：计划层 `m`（可显式 `mm`），执行层统一换算，报告必须写明所用单位。
- 段索引：0 基，与 `segments` 顺序一致；闭合路径最后一段连回首点。
- 每个几何产物需带 **几何哈希**（B 负责定义算法，D 负责记录），用于"同一案例不同版本"的可比性。
- 坐标容差语义分三层：`connection_tolerance`（端点拼接）、`tangent_tolerance_deg`（切线夹角）、`max_sampling_error`（曲线离散误差）。三者不可混用。

### 5. Execution Context（执行上下文）

- 现状：`agent_service.py` 提供 `set_request_execution_context` / `reset_request_execution_context`，`agent_http_service.py` 在各入口注入并原样透传 `execution_context` 字典（prepare / 执行 / 结果三处都会带出）。
- 冻结语义（字段命名以 C 分支现状为准，**语义不可变**）：必须能唯一区分五件事——`request_id`、`conversation_id`、`project_id`、`variant_id`（候选/版本）、`contract_version`。
- 生命周期：请求进入时注入，请求结束（含异常路径）必须清理；并发请求不得共享同一份可变上下文。
- 其它线只读：A/B/D 不得写入或重组 `execution_context`。

### 6. Evaluation（评测记录）

D 定义并维护，字段至少包含：`case_id`、`model`、`policy`、`request_id`、`usage`（token）、`finish_reason`、`geometry_hash`、`H2` / `H3` / `H4` 三态结论、`final_candidate_state`、`cost`。其它线只消费，不改字段含义。

## 四、接口变更流程

1. 提案人写 `backend/evaluations/parallel/proposals/YYYYMMDD-<主题>.md`，内容必须包含：动机、现状、拟改字段、受影响调用方清单、迁移方案、回滚方案。
2. 总控审批；审批前不得改代码，也不得"先加字段再补提案"。
3. 获批后由**单一负责人**修改，同批更新受影响的测试与文档。
4. 变更必须在一个独立 commit 里，commit message 以 `interface:` 开头，便于集成时识别。

## 五、发现越界怎么办

- 发现别的线改了自己所有的文件：不要回退对方提交，先在汇报里列证据（文件 + 行 + commit），由总控处理。
- 发现自己的改动必须触碰禁改文件：停下来提需求或提案，不要"就改一行"。
- 发现共享文件本身有 bug：记录证据，交给负责人；紧急情况下（阻塞全部四条线）由总控裁定临时 owner。
