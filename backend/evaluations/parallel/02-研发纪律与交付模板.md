# 研发纪律与交付模板

## 一、共同纪律（14 条，逐条可检查）

1. 开工前先读基线代码与相关报告，不凭印象改。
2. 动手前列出「准备修改的文件」，并对照 `01` 确认全部在自己所有权内。
3. 不修改其它线所有权范围内的生产文件。
4. 每个功能配套独立测试；没有测试的功能不算完成。
5. 每个可独立回滚的改动单独一个 commit，不把不相关的修改混在一起。
6. 不删除历史失败测试，失败样本继续保留并标注。
7. 不放宽已有验收标准（阈值、判据、断言数量）。
8. 不覆盖其它线的测试数据与结果文件。
9. 不在共享生产数据库上跑测试；一律用临时库/内存库。
10. 不擅自修改公共接口（见 `01` 的提案流程）。
11. 发现接口冲突提提案，不私下兼容两套字段。
12. 发现其它模块有问题只记录证据，不越权修改。
13. 不 `git add -A`；提交用显式路径。
14. 不 push、不合并 main、不 `git reset --hard` 别人的分支。

## 二、Git 操作规范

- 只在**自己工作树根**执行 git 命令（不要在 `backend/` 子目录里执行，见 `README` 环境注意第 3 条）。
- 分支：`parallel/nlp-planning`、`parallel/geometry`、`parallel/orchestration`、`parallel/evaluation`。不新建其它并行分支，需要实验分支时用 `exp/<主线>-<主题>` 并在汇报中说明。
- 提交信息格式：

```
<type>(<line>): <一句话结论>

- 动机：为什么改
- 范围：改了哪些文件（可缩略为目录 + 关键文件）
- 验证：跑了什么命令，结果如何
- 影响：是否触碰公共接口（是则附提案路径）
```

`type` 取 `feat` / `fix` / `test` / `docs` / `chore` / `refactor` / `interface`；`line` 取 `nlp` / `geometry` / `orchestration` / `evaluation`。

- 接口类改动必须单独提交，`type=interface`，便于集成时先审。

## 三、测试要求

- 单元/回归：`cd backend` → `python -m pytest tests -q`
- 单文件：`python -m pytest tests/test_cad_construction.py -q`
- 只跑自己新增的：`python -m pytest tests -q -k "nlp"`（按你的前缀替换）
- 真实模型调用：默认禁止；必须走 `04` 的准入流程，且在专用工作树/专用账本记录。
- 测试必须能在无网络、无真实模型时通过；需要模型的用例用 Mock 或录制回放。

首次开工先建环境（每棵树一次）：

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r backend\requirements.txt
```

## 四、阶段汇报模板（提交时同时写进自己的报告文件）

```markdown
## 阶段：<诊断 / 实施 / 收口>  <日期>

### 1. 修改文件
- backend/app/xxx.py：<一句话改动目的>
- backend/tests/test_xxx.py：新增 N 个用例

### 2. 新增/变更接口
- 函数 `f(a, b) -> dict`：调用方 `g`
- 字段 `x`：是否有提案（路径）

### 3. 提交
- `<commit hash>` `<commit 标题>`

### 4. 测试
- 命令：`python -m pytest tests/test_xxx.py -q`
- 结果：X passed / Y failed
- 失败项是否为本轮引入：是/否（附证据）

### 5. 未解决
- <问题>：<已排除的原因> / <下一步>

### 6. 对其它主线的依赖
- 依赖 A 的输出字段 `xxx`（当前状态：已存在 / 待提提案）

### 7. 合并冲突风险
- 预计冲突文件：<无 / 文件名>；原因：<共享接口 / 同一文件>
```

## 五、收口前自检（缺一项不算完成）

- [ ] 我在自己分支上，`git status` 干净（除未跟踪的本地临时文件）。
- [ ] 我改的每个文件都在 `01` 的允许范围内。
- [ ] 我新增的行为都有测试，且测试在干净环境下能跑通。
- [ ] 我没有放宽任何既有阈值。
- [ ] 我的报告里有可复现命令，而不是结论截图。
- [ ] 我列出了本轮**没有**验证到的部分。

## 六、禁止事项（触及即打回）

- 为单个案例写特判/硬编码坐标。
- 改冻结样本（A9/S1/M1 的输入与历史结果）。
- 用 `--no-lint` 式的"绕闸"手段让测试变绿（例如跳过断言、mock 掉验收）。
- 在别人的分支上提交、强推、重置。
- 把 `backend/evaluations/reports/**` 的新产物写进仓库根或其它线目录。

## 七、第一阶段：只读纪律（硬约束）

**允许**

- 读代码、文档、历史评测产物；复制数据到本地临时目录做离线复算。
- 在自己工作树建 `scratch/` 放临时脚本与数据（不入库）。
- 跑现有测试、跑 Mock、跑零费用复算。
- 写自己的第一阶段报告。

**不允许**

- 改 `backend/app/**` 下任何文件（D 为全目录禁改，A/B/C 只在自己所有权内、且阶段一仍不改）。
- 改冻结样本、改测试断言、改公共接口。
- 调真实 DeepSeek（唯一例外：D 在授权额度内跑基线，且必须记账）。
- 在别人分支提交、`git add -A`、`git push`。

**阶段一结束的机械判据**（四条命令都要跑，缺一条不算验收）：

```powershell
git -C <树> status --short
git -C <树> diff --stat <起点>..HEAD
git -C <树> diff --cached --stat
git -C <树> ls-files --others --exclude-standard
```

判读：

- 未跟踪文件只允许第一阶段报告（`.md`）与 `scratch/` 下的临时内容；两者都算合规。
- `git diff --stat` 只允许出现本目录的报告文件；`backend/app` 出现任何条目即不合格。
- 出现其他主线的文件，立即停止并调查，不要先 `git checkout --`。
- **注意**：`git diff --stat` 不显示未跟踪文件，只看它会把"新建了报告"误判成"什么都没做"；只看 `status --short` 又分不清报告和代码改动。必须四条合起来看。

达不到这个判据，第二阶段不予批准。D 在第一阶段同样不新建 `bench/` 目录、不建账本文件。

## 八、证据门槛（没有证据 = 待验证）

| 主线 | 必须交付的证据 |
|---|---|
| A | 原始请求、原始响应、字段首次缺失的源码位置（文件:行）、该位置上下游调用链 |
| B | 两段 Bezier 的参数区间、交点坐标与误差上界、可一键复现的复算脚本 |
| C | 候选 id、来源 id、版本号、完整调用链（请求 → 服务 → 落库） |
| D | 现有评测工具清单与缺口、三案例输入一致性核对（含哈希）、账本字段缺口、Mock 可跑性结论 |

通用规则：结论必须同时具备 **源码位置 + 原始记录 + 可复现命令**。三者缺一，标记为「待验证」，不得写进报告的结论段，也不得作为第二阶段立项依据。

## 九、第二阶段准入（总控审批，不自行开工）

流程：A/B/C 先交第一阶段报告 → 总控逐条归类：

| 归类 | 处理 |
|---|---|
| 根因明确，只需改现有函数 | 批准，限定文件与函数范围 |
| 必须改公共 Schema | 先走 `01` 的提案，批准后由单一负责人改 |
| 只需改提示词/规划策略 | 批准，但必须附「改动前后同一案例对照」的验收方式 |
| 根因仍不明确 | 打回继续诊断，禁止"边猜边改" |

审批结论写进 `06`。**未经批准，四条线一律停在只读阶段。**
