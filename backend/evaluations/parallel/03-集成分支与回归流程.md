# 集成分支与回归流程

集成分支：`integration/p1.4-parallel`，对应工作树 `cad-worktrees/integration`。**只有总控在这里操作**；四个 Agent 不得自行合并。

## 一、为什么不让 Agent 直接合 cad

- 四条线共享五个接口（`01`），任何一条擅自合并都会把别人的输入输出改掉。
- 合并必须伴随回归；Agent 各自只跑自己那部分测试，无法给出全局结论。
- `cad` 是当前研发主线，被未回归的提交污染后，回滚成本高于重跑一次集成。
- `main` 是另一条独立开发线，本轮全程只读，不参与合并，也不推送。

## 二、合并顺序（按依赖，不按完成先后）

1. `parallel/evaluation` —— 先把 Benchmark 与账本工具带进来，后面每次合并都能立刻量化。
2. `parallel/nlp-planning` —— 改的是计划产出，影响 B 的输入，先合先暴露几何回归。
3. `parallel/geometry` —— 依赖 A 的输出语义，必须在 A 之后。
4. `parallel/orchestration` —— 消费 A 与 B 的结果，最后合，避免链路层掩盖上游问题。

顺序可调整，但必须写进当日 `06-每日集成记录.md` 并说明理由。

## 三、逐步操作

```powershell
cd D:\xikao\cad-worktrees\integration
git status --short            # 必须干净，否则先停下
git log -1 --oneline
git merge --no-ff parallel/evaluation
```

每合一条线，立刻做三件事：

1. **接口检查**：`git diff --stat <base>..HEAD` 看是否触碰 `01` 里冻结的字段；有 `interface:` 提交则先读提案。
2. **专项回归**：跑该线对应的测试子集 + 受影响的相邻线子集（例如合 A 后要跑几何验收）。
3. **记录**：把结果写进 `06`，包括失败项归因。

四条线全部合完，再做一次完整回归（见第五节）。

## 四、冲突处理规则

- 同一文件冲突：**不自动解决**。先看 `01` 的所有权表，由文件负责人给出"保留哪一边 + 为什么"，总控执行。
- 接口字段冲突（两边都加/都改名）：直接拒绝合并，退回提案流程。
- 测试文件冲突：以被测模块负责人的版本为准，另一方的新增用例要保留则改为新文件。
- 冻结样本/阈值冲突：一律以基线为准，任何"顺手调了阈值"的提交直接打回。
- 冲突解决后必须重跑该线专项回归，不能只 `git add` 了事。

## 五、完整回归清单（每条都要有输出证据）

| # | 项 | 命令 / 方式 | 通过标准 |
|---|---|---|---|
| 1 | 全量单测 | `cd backend` → `python -m pytest tests -q` | 无本轮新增失败 |
| 2 | P0 信任边界 | `python -m pytest tests/test_cad_p0_trust_boundary.py -q` | 全绿 |
| 3 | 冻结案例 A9 | 按 D 的 Benchmark 运行器跑 A9 | 结果与基线可比，差异有解释 |
| 4 | 冻结案例 S1 | 同上 | 确定性路由仍生效 |
| 5 | 冻结案例 M1 | 同上 | 折角意图仍被识别 |
| 6 | 两轮 HTTP 闭环 | C 的闭环测试 | 候选保存 + 第二轮继承来源均通过 |
| 7 | 接口一致性 | 对照 `01` 五个接口逐项核对 | 无未报批变更 |
| 8 | 指标对比 | 见 `05` 三个指标 | 至少一项有实质提升，或明确记录"无提升及原因" |
| 9 | 无越界改动 | `git diff --stat` 对照所有权表 | 无他人文件被改 |

## 六、最终集成报告必须回答

1. 四条线各自带来什么可测量的变化（用 `05` 的口径）。
2. 哪条线没有带来变化，为什么保留它。
3. 五个接口是否仍然一致；有无技术债（例如两套字段并存）。
4. 哪些结论是 Mock/离线得出的，哪些是真实模型得出的，各自覆盖多少案例。
5. 下一轮（P1.5）最该先做什么，依据是什么。

## 七、回滚

- 单条线有问题：`git revert -m 1 <merge-commit>`，不重置分支历史。
- 整轮失败：保留 `integration/p1.4-parallel` 现场，另起 `integration/p1.4-parallel-r2` 重来，不删旧分支（保留证据）。
- 禁止用 `git reset --hard` 清理集成分支。

## 八、合入 cad 的最终步骤（含差异检查）

前置条件：第五节九项回归全部通过，`06` 已写收官条目，且用户已确认可以合入。

### 1. 差异检查（只读，在主工作树执行）

```powershell
git -C D:\xikao\xikao1_-app log --oneline 211cacd..cad
git -C D:\xikao\xikao1_-app diff --stat 211cacd..cad
git -C D:\xikao\xikao1_-app log --oneline cad..integration/p1.4-parallel
git -C D:\xikao\xikao1_-app log --oneline integration/p1.4-parallel..cad
```

判读规则：

- 第 1、2 条非空：说明并行期间 `cad` 上确实有新提交（文档提交也算），逐条确认它们是否已被集成吸收。
- 第 4 条非空：**这是危险信号**——`cad` 上有集成分支没有的提交，直接合入会丢改动或产生非预期覆盖。此时必须先回到 integration 工作树执行 `git merge --no-ff cad`，解决冲突并重跑九项回归，再走第 2 步。
- 第 4 条为空：`cad` 未前进，可以安全合入。

### 2. 合入

```powershell
git -C D:\xikao\xikao1_-app merge --no-ff integration/p1.4-parallel
```

注意事项：

- **不要 `git push`**，合入后停在本地，等用户确认再推。
- **不要在 integration 工作树里 checkout `cad`**：`cad` 已在主工作树检出，git 会直接拒绝；合入动作只能在主工作树做。
- 若出现冲突，退回第四节处理，不允许在 `cad` 上直接手改后提交。

### 3. 合入后二次回归（不能省）

合并提交会改变树状态，必须在 `cad` 上再跑一次最小集：

1. 全量单测；
2. P0 信任边界；
3. A9 / S1 / M1 三案例；
4. 接口一致性对照（`01` 五类接口）。

二次回归通过，才算"已交付"。

### 4. 记录与收尾

- 在 `06` 写：合入 commit、九项回归结论、二次回归结论、**未推送**状态。
- `main` 保持原样；不创建指向 main 的合并、不推送 main。
